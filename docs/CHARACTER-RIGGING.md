# 3D character rigging

**Current benchmark:** [Basalt Warden](media/character-qualification-2026-10/basalt-corrected-humanoid/README.md) has approved body deformation, a valid Unity Humanoid Avatar and evaluated diagnostic animation. Rigging providers remain experimental; full material/input qualification and third-party motion validation are outstanding. Dated failures below remain historical evidence.

## Animation-readiness gate

Run deterministic mesh inspection after approving a character model and before requesting a rig:

```sh
slopforge --project ~/UnityProjects/MyGame character readiness moon_scout_character
slopforge --project ~/UnityProjects/MyGame inspect moon_scout_character
slopforge --project ~/UnityProjects/MyGame character approve-readiness moon_scout_character
slopforge --project ~/UnityProjects/MyGame character normalize moon_scout_character
slopforge --project ~/UnityProjects/MyGame character approve-normalization moon_scout_character
slopforge --project ~/UnityProjects/MyGame character readiness moon_scout_character --source-output normalized_model
slopforge --project ~/UnityProjects/MyGame character approve-readiness moon_scout_character
slopforge --project ~/UnityProjects/MyGame character rig moon_scout_character --source-output normalized_model
```

The report records topology, connected components, transforms, face normals, bounds/scale, face budget, source artifact, and source SHA-256. `pass` still requires explicit approval; `needs_review` requires human approval after reviewing the evidence; `fail` cannot be approved. Rigging is blocked until the report is accepted. The manifest keeps model generation, animation readiness, rigging, deformation, and Unity Avatar states separate. This gate checks mesh structure and scale; it does not establish anatomy, useful skin weights, acceptable deformation, or Unity Humanoid validity.

Normalization is a separate, reviewable stage. It welds/remeshes components, creates UVs, and bakes available source material channels; inspect its report and compare it with the source before approval. Run readiness again against `normalized_model` and approve that report before rigging with `--source-output normalized_model`. The original generated model remains intact. Remeshing and baking can reduce visual fidelity; normalization cannot invent missing detail or repair a bad character design.

Rigging is a separate character stage; prop cleanup does not create a deformable skeleton. New projects include a first-class `character` model type and the `character_3d_pack` recipe. It generates one full-body neutral A-pose concept, runs the selected 3D model workflow, and records a reviewable model on a character asset. Configure `asset_pipeline.character_rigging_provider` as `blender_rigify` or `skintokens`. SkinTokens runs from a separately configured Python environment, checkout, and checkpoint; `character provider-setup skintokens` applies only the pinned, hash-checked compatibility edit to that checkout.

```sh
slopforge --project ~/UnityProjects/MyGame recipe run character_3d_pack --name moon_scout
slopforge --project ~/UnityProjects/MyGame candidates moon_scout_character
slopforge --project ~/UnityProjects/MyGame approve moon_scout_character 1
slopforge --project ~/UnityProjects/MyGame approve-texture moon_scout_character 1
slopforge --project ~/UnityProjects/MyGame character rig moon_scout_character --source-output normalized_model
```

Provider outputs can be recorded with `slopforge.character_rigging.record_rigging_result()` as typed artifacts on a `character` manifest asset. The result names an already approved source output, a project-relative FBX or GLB, optional PNG pose evidence, skeleton-name mapping, and provider provenance (`name`, `version`, `source`, and `license`). Registered rig and evidence artifacts remain candidates pending human review.

The recorder rejects paths outside the project, missing/empty exports, unapproved source artifacts, unsupported mesh formats, invalid evidence images, and incomplete provider license metadata. It records missing recommended pose evidence without pretending the rig passed deformation checks. Suggested evidence poses are T-pose, raised arms, crouch, leg lift, elbow bend, and shoulder rotation.

## Blender Rigify provider

With `blender_rigify` selected, `slopforge character rig <name> [--source-output model]` runs Blender's bundled Rigify add-on against a ready, approved GLB or FBX model artifact. It fits Blender's human metarig to the model bounds, welds coincident vertices, reports boundary edges, rejects non-manifold edges, generates automatic weights, renders six review poses, measures vertex displacement, and exports an FBX. Boundary edges are open surface edges; readiness flags them for human review, but they are not treated as non-manifold edges by the Rigify guard. Rig and pose artifacts are registered as pending review; the command never approves them.

The provider uses the installed Blender executable and its bundled code; no extra Python package or model weights are installed. The provider reports Blender/Rigify version and GPL-2.0-or-later provenance. Review the installed Blender distribution's notices for the exact bundled add-on terms.

This is a fitting heuristic, not general-purpose automatic rigging. It expects an upright humanoid whose proportions fit Blender's human metarig; bounds-based fitting cannot place joints reliably for arbitrary anatomy. Vertex welding can alter the mesh slightly. The synthetic Blender integration smoke verifies execution, weighting, export, and pose motion, but does not establish quality on generated SlopForge characters. Inspect the source, rig, and all six pose renders before approval; pose images and nonzero displacement do not establish acceptable deformations or Unity Humanoid compatibility.

The recipe reuses SlopForge's configurable image-to-3D model provider; it does not guarantee anatomical correctness, an animation-ready pose, or a closed manifold. Rigify remains a bounds-fitted humanoid heuristic and rejects true non-manifold edges; open boundaries are reported and remain subject to readiness review. SkinTokens is available as an opt-in provider, but its runtime and checkpoint must be configured explicitly and its results remain experimental. The reviewed Basalt candidate now has body-deformation approval and Unity Humanoid evaluation; complete production qualification remains open. SkinTokens checkpoint training-data rights also remain unresolved; see [the provider audit](research/unirig-rigging-provider-audit.md).

Character mesh candidates need review when Blender reports more than 64 connected components, boundary edges, or any non-manifold edge after duplicate-vertex welding. The component limit is configurable on the character asset type. These checks do not repair geometry, and passing them does not prove good skinning, deformation, or texture coverage.

The H100 character smoke on 2026-10-04 produced a TRELLIS.2 BF16 scout mesh with 1,189 disconnected components and 15,402 boundary/non-manifold edges under the then-current combined classification, with visible missing surfaces in the three-view review. It was kept unapproved and was not rigged. A Hunyuan3D comparison produced a more complete single-component mesh; the then-current inspection reported 4,168 non-manifold edges after welding, but that count also included boundary edges and must be remeasured with the corrected classification before drawing a non-manifold conclusion. A same-mesh disposable comparison showed severe limb distortion in several Rigify poses. The isolated SkinTokens provider produced a 34-bone rig with normalized weights and a better-looking bilateral elbow pose on this same candidate. Its cleaned FBX imported into Unity 6000.6.3f1 as Generic with 34 bones and 34 bind poses; animation playback was not tested. The input still fails readiness, its material was neutral gray, the output has not passed human review, and the inference environment needed a temporary attention-backend patch. Evidence and limits are in the [provider audit](research/unirig-rigging-provider-audit.md). Issue #14 remains open pending a readiness-passing textured generated character, qualified runtime, deformation review, and Unity animation validation.

A disposable Blender 5.1 voxel-remesh probe on the Hunyuan candidate removed its measured non-manifold edges (19,582 vertices, 28,500 faces, one component), and the resulting mesh passed the structural readiness report. This did not fix animation quality: a real Rigify run completed but its six-pose sheet shows extreme elbow/shoulder and limb distortion. A triplanar bake from the original single-view concept repeated the image across the model and is not usable texture coverage. The files and measurements are preserved under `~/Downloads/SlopForge-H100-character-rig-20261004/results/voxel_remesh_rigify_probe/`; all remain disposable, unapproved evidence. This confirms that topology repair alone cannot make the generated model rig-ready.

SkinTokens was then run on that remeshed GLB in its isolated H100 checkout. Its 28-bone output had no unweighted vertices, at most four influences per vertex, and weight sums from 0.99999986 to 1.00000012. Actual elbow/arm pose renders look materially better than the Rigify result on this input. The GLB still has nine disconnected mesh components, a hidden unskinned helper, no material, and pending review. Its cleaned FBX imported into Unity 6000.6.3f1 as Generic with one skinned renderer, 28 bones, and 28 bind poses; no animation or playback was tested. This is stronger provider evidence, not a qualified or approved character; exact source/checkpoint hashes and output are recorded in the provider-audit evidence folder linked above.

The Unity import path is verified against a watertight synthetic Rigify fixture: Unity 6000.6.3f1 populated the Humanoid skeleton, accepted the explicit Rigify bone map, imported a matching animation clip, and created a controller and prefab with a valid Humanoid Avatar. The SkinTokens Generic import separately confirms the 34-bone skinned mesh is accepted by Unity, but no animation playback was tested. These checks do not qualify the generated H100 character; its input still fails readiness and its rig remains unapproved.

## Normalization contract probe — 2026-10-06

A disposable normalization of the existing Hunyuan scout produced one mesh (6,588 vertices and 6,586 faces in the Blender report) and a 256×256 base-color bake. The input had no roughness, metallic, or normal maps, so those channels were absent. Blender inspection measured zero boundary/non-manifold edges and one connected component, but matched source/normalized renders show severe faceting and loss of small character details. This coarse candidate is rejected on visual quality and was not rigged. Do not approve normalization based on structural readiness alone; see the retained [qualification evidence](media/character-qualification-2026-10/README.md).

The resolution formula was then corrected to account for GLB triangulating voxel-remesh quads. On the same input, the checked-in normalizer produced 28,688 Blender faces / 57,376 GLB triangles, one connected component, and zero non-manifold edges; the imported model passes the configured 60,000-triangle readiness budget. Matched Blender renders retain the source silhouette and suit details substantially better than the coarse result. Rigify completed but its six-pose contact sheet still shows severe limb distortion. SkinTokens was subsequently rerun on this exact normalized mesh; its first contact sheet shows less obvious stretching, but the current automatic pose controls do not yet prove anatomically correct joint motion. The candidate remains unapproved and Unity playback is still pending. See the retained [qualification renders and reports](media/character-qualification-2026-10/README.md).

### Same-mesh SkinTokens comparison — 2026-10-06

The isolated SkinTokens checkout at `273b691d35989d71cd17ff2895fdc735097b92d1` ran on the readiness-passing normalized GLB on the H100 with the existing SDPA compatibility shim and `--use_transfer`. The inference completed in about 12 seconds. The output contains one armature with 28 bones. Blender packaging identified and removed the known unskinned helper, transferred the only available source map (base color, 100% vertex coverage), and welded 88,626 exact per-triangle duplicate vertices at `1e-7`: the mesh went from 117,314 vertices / 29,969 components to 28,688 vertices / one component, preserving all 57,376 faces. All vertices have weights, at most four influences, and weight sums from `0.99999985` to `1.00000013`.

The matched elbow render shows less visible stretching than the Rigify result. The pose set still does not establish production deformation quality: the current tests use direct Euler rotations on inferred semantic bones, and the rendered poses do not consistently demonstrate the named human motions. Do not promote this rig or proceed to Unity playback based on this sheet. First make the diagnostic poses anatomically meaningful, then review a readable multi-view contact sheet. Evidence, exact hashes, and reports are in [`same-mesh-budget-skintokens`](media/character-qualification-2026-10/same-mesh-budget-skintokens/).
