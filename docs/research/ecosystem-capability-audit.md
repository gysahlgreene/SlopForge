# Ecosystem capability audit

**Audit date:** 2026-10-05
**Repository state:** `codex/prototype-content-factory`, HEAD `5716d8e` plus pre-existing uncommitted integration work. This audit did not reset, stage, or modify those changes.
**Scope:** fresh web/source review of game-asset orchestration, ComfyUI, sprites, image-to-3D, rigging/retargeting, DCC/engine sync, and environment workflows. This is not a controlled provider benchmark.

## Method and confidence

I reviewed first-party repositories, their READMEs, implementation/workflow files, license files or model cards, available issues/release/activity pages, and SlopForge's current source and evidence documents. “Works” below means an upstream implementation, workflow, test, or artifact was inspected; it does not mean it was run against SlopForge's benchmark assets. Upstream demonstrations and SlopForge's own tests are kept separate from live, visual, and engine qualification.

Twenty-six projects/toolchains were investigated as serious candidates or reference implementations. Nine superficially relevant repositories were set aside from the decision matrix after source/code/license/evidence checks found a prompt wrapper, hosted API example, thin MCP bridge, or no runnable end-to-end asset path. A complete dated search-result dump was not retained; the reject count is therefore a screened-candidate count, not a count of every search hit.

License labels in upstream metadata are not a substitute for auditing all transitive packages, checkpoints, datasets, output terms, or subdirectories. “Unknown” is intentionally used where first-party evidence did not settle those rights.

### Maturity scale used for SlopForge

- **NOT IMPLEMENTED** — no working path or explicit contract.
- **CONTRACT ONLY** — interfaces/config/data model exist; no demonstrated real output.
- **MOCK VERIFIED** — offline tests use mocks/fixtures only.
- **STRUCTURALLY VERIFIED** — deterministic output shape/constraints checked, but no real model output or visual judgment.
- **LIVE VERIFIED** — a real provider completed a run; output usability not implied.
- **VISUALLY VERIFIED** — a real output was inspected for the stated purpose.
- **ENGINE VERIFIED** — imported or played in the target engine for the stated purpose.
- **PRODUCTION CANDIDATE** — repeatable quality, legal terms, runtime, recovery, human review, and target-engine criteria are all demonstrated. No current AI generation path reaches this level.

## Deep implementation notes

### 1. Sprite pipeline details

The most useful external work is the sequence, not a claim that one model solves animation. `comfyui-2d-character-pipeline` has one API workflow for posing a character from a COCO-18 keypoint map, another for Wan 2.2 I2V from the posed image, and a later workflow for video-frame matting and fixed 128-pixel cells. Its W2 graph uses two Wan experts with staged sampling; a small custom VRAM helper unloads the high-noise expert and clears cached model patches before loading the low-noise expert. The thin Python drivers submit API-format workflows, poll history, choose the newest versioned output, and pass the video filename to W3. The project reports a 33-frame idle run plus walking/in-air samples on one character and a peak under 20GB on RTX 3090; no automated tests or Unity playback were found. It also records a WAN replacement test that failed to preserve motion/invented legs. W2 conditions only the first keyframe, so later-pose consistency remains a risk.

The repo and its VRAM helper are MIT. W1 uses Qwen-Image-Edit-2509, Wan and Lightx2v artifacts labeled Apache-2.0. W3's `ComfyUI-RMBG` node pack is GPL-3.0; its selected ToonOut BiRefNet checkpoint is labeled MIT, but a separately auto-downloaded 1038lab mirror has no model-card license metadata. SAM3 is only needed for later cosmetic-layer workflows, uses Meta's custom license, and is not part of the base W1–W3 test. Treat the W1–W3 graph as a **REFERENCE IMPLEMENTATION / ADAPT** candidate; use a separately licensed matting implementation or a pinned verified MIT checkpoint rather than inheriting ambiguous automatic downloads. The upstream Windows paths/local ComfyUI assumption must be adapted to SlopForge's HTTP upload/queue/download interface.

The independent `sprite-gen` technique is valuable after frame generation: generate one image per state/row, extract cells deterministically, curate/select weak frames, align on an alpha-weighted centroid or foot-line anchor, and write frame/run manifests. Its extraction path includes connected-component/DP segmentation, optional YCbCr chroma matting with edge despill/self-checks, and atomic writes guarded by a single-writer lock. This is much more mature than the current fixed-grid packager for uncertain source layouts. Its test suite covers deterministic byte contracts and pipeline components, but generation quality remains tied to providers. The package is Apache-2.0 and NOTICE attributes ports from MIT `perfectpixel-studio`; preserve both if source is adapted. Current release/tag and branch package metadata disagree, so verify the selected release artifact before installing. The image/video providers use Codex/OpenAI/xAI credentials and remote services; they are not open local generation models and their costs/terms are independent.

`envy-ai/sprite-generator` attacks direction-sheet slicing from frames by building a union alpha mask over selected frames and locating persistent connected blobs, then cutting at midspaces. This is a heuristic that can fail with overlapping limbs or detached accessories; the upstream implementation is AGPL-3.0-only and should be treated as a behavior reference unless SlopForge accepts its copyleft terms.

**Decision:** SlopForge's TI2V output failed review and its Wan Animate dance was explicitly rejected by the user. Stop polishing those graphs. First reproduce the external W1→W2→W3 workflow with the same goblin identity and idle/walk/attack, in an isolated/pinned environment; separately test `sprite-gen` on the resulting frames and the SlopForge packager. Compare generation and frame cleanup separately. No provider should be selected from README screenshots or a single idle. Unity playback remains a final gate.

### 2. Character mesh → rig → usable deformation

Treat #14 as distinct stages with explicit failure ownership:

```text
generated mesh + texture
  → identify intended character mesh and helper objects
  → preserve/repair UVs and material inputs
  → normalize units, axis, transforms and known rest pose
  → structural/readiness report and human acceptance
  → rig-provider skeleton + weights
  → validate bones, bind pose, weight coverage/normalization and components
  → standardized deformation poses + visual contact sheet
  → FBX/GLB export and Unity Generic/Humanoid import
  → animate and visibly play clips in Unity
```

SlopForge's current evidence says SkinTokens beats its current bounds-fitted Rigify result for the tested elbow/arm pose. That does not establish a winner because input mesh/component/material defects are still present and no clip played. Retain SkinTokens as the leading isolated candidate, Rigify as the no-weight baseline, and require the same readiness-passing textured input for any comparison. UniRig's separated skeleton/skinning steps reinforce that a skeleton should be reviewable before weights. Research code that only predicts skeletons or is noncommercial is not a usable default.

### 3. Workflow versioning and executable environments

Official ComfyUI template metadata separates template discovery from inference and can declare minimum ComfyUI version. SlopForge's adjacent sidecar already captures many essentials and is better tailored to packaging provenance. It does not capture installed custom-node commit, model content hash, dependency lock, or exact environment container. Comfy MCP supplies model/node search, editable slots and queue diagnostics, but licensing changed from Apache to AGPL/commercial; its changelog also demonstrates that slot parameter mapping itself can mispair. Keep the SlopForge HTTP client and sidecars; add version/environment pins only when the provider exposes stable IDs and a reproducible way to query them.

### 4. Engine identity and replacement

Unity provides `.meta` GUIDs and native importer settings; SlopForge should own stable logical asset IDs and deterministic output paths, then let Unity own `.meta` and imported artifacts. Add a hash over source files plus importer settings to evidence. Use the Editor API / `AssetPostprocessor` for importing, remapping and `SaveAndReimport`; do not regenerate IDs by rewriting `.meta`. Unity's own import-consistency tooling should be an opt-in integration test, not a requirement for offline tests.

## Screened out as superficial or unsuitable

Nine first-pass candidates did not qualify as strong evidence of reusable end-to-end implementation: several were prompt-to-API demos that only invoke hosted generators, some were agent-role collections without a machine-checked asset artifact contract, and some were MCP tools exposing arbitrary Blender operations without a deterministic pipeline or validation corpus. They remain possible UX ideas, not pipeline evidence. An agent count, successful API response, polished landing page, or generated static screenshot did not count as live animation, deformation, or engine verification.

## Limits and open questions

- No shared original test character was run through external candidate pipelines during this audit. Existing SlopForge H100/Blender/Unity evidence is documented separately and is not presented as an external bake-off.
- Model and video-generation output terms may differ from source-code licenses. The actual selected Wan/Qwen/BiRefNet files, quantized conversions, and custom node directories must be verified before any workflow import.
- Recent projects have volatile `main` branches. Their branch tip should be pinned by commit before a repeatable benchmark or code dependency is approved.
- The ecosystem did not reveal a single permissively licensed, fully local, reproducible system that already satisfies SlopForge's plan approval, local/remote ComfyUI, provenance, budget, review, and Unity requirements end-to-end.
