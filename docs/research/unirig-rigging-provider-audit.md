# Automatic rigging provider audit: Rigify, UniRig, and SkinTokens

**Checked:** 2026-10-04. Sources below are first-party repositories/model cards, the authors’ papers, or platform documentation. This is a compatibility and license inventory, not an inference test or legal opinion.

## Finding

SlopForge now has an opt-in local rigging path through Blender's bundled **Rigify** add-on. It has no model weights or separate runtime and was exercised with a synthetic Blender humanoid fixture. It is a bounds-fitted humanoid heuristic, not a learned provider; the smoke test does not establish quality on generated characters. See [3D character rigging](../CHARACTER-RIGGING.md).

For a learned provider, **SkinTokens / TokenRig** remains the first candidate for a separate opt-in integration; the UniRig maintainers identify it as UniRig's successor. SkinTokens combines skeleton and skin-weight prediction, publishes inference code and checkpoints, and documents an NVIDIA GPU requirement of 14 GB. UniRig remains a useful reference because it has an MIT codebase and explicit staged skeleton/skin/merge commands, but its README says checkpoint releases are progressive and its model card is internally inconsistent about which components/checkpoints are actually available.

This is a candidate, not an approved production provider: neither project establishes reliable deformation for arbitrary SlopForge-generated characters, and dataset/model training-data commercial rights are not fully documented in the reviewed sources. Rig review and explicit user approval must remain in the pipeline.

### UniRig release ambiguity

The [repository README](https://github.com/VAST-AI-Research/UniRig/tree/6793c6640ff01c8fb389f3993434124bb43d2933#current-release-status--roadmap) says skeleton and skinning prediction code/checkpoints are available progressively. The [Hugging Face card](https://huggingface.co/VAST-AI/UniRig) says only the skeleton-prediction checkpoint is included and says skinning checkpoints are coming; however, the model repository file listing contains `skin/articulation-xl/model.ckpt`. The reviewed sources do not explain this discrepancy or establish which checkpoint is supported by the documented inference scripts. Treat UniRig as requiring an upstream smoke test before integration.

## SkinTokens / TokenRig (recommended candidate)

| Area | Verified from upstream |
|---|---|
| Source and status | [Official VAST-AI-Research/SkinTokens repository](https://github.com/VAST-AI-Research/SkinTokens/tree/273b691d35989d71cd17ff2895fdc735097b92d1), reviewed `main` commit. Maintainers call it UniRig’s successor. Its [model card](https://huggingface.co/VAST-AI/SkinTokens) identifies TokenRig and the FSQ-CVAE checkpoints and documents download/inference commands. |
| Software/model license | [Code license](https://github.com/VAST-AI-Research/SkinTokens/blob/273b691d35989d71cd17ff2895fdc735097b92d1/LICENSE) and [checkpoint model card](https://huggingface.co/VAST-AI/SkinTokens) declare MIT. The architecture fetches [Qwen3-0.6B](https://huggingface.co/Qwen/Qwen3-0.6B), whose model card declares Apache-2.0. No reviewed source grants comprehensive rights to all training assets: the checkpoint card reports training on ArticulationXL 2.0, VRoid Hub, and ModelsResource, while the processed training data is described as a separate/future release. Check those dataset and asset terms before commercial deployment; MIT metadata alone does not settle them. |
| Hardware / platform | README specifies Python >=3.11, CUDA Toolkit >=12.1, and NVIDIA GPU memory >=14 GB. This fits an H100 80 GB on stated memory requirements. It does not publish an OS support matrix. Its demo contains a Windows-specific subprocess branch, while installation and scripts are shell-oriented; Windows support is therefore not established end-to-end. |
| Dependencies / runtime shape | Requirements include `bpy>=4.2`, `trimesh`, `open3d`, `transformers>=4.57.0`, Lightning and others. `demo.py` launches `bpy_server.py` as a child process and sends mesh data to it; isolate its Python/CUDA/Blender dependencies from ComfyUI rather than installing this stack into ComfyUI’s environment. A complete transitive dependency license audit has not been done. |
| Inputs and outputs | `demo.py` accepts `.obj`, `.fbx`, `.glb`; CLI examples write `.glb`. Options support using an existing skeleton, transferring original texture/scale, and voxel-based skin postprocessing. This is an offline CLI/local Gradio workflow, not a ComfyUI node or HTTP provider. |
| Blender / Unity | It uses Blender’s Python module as a processing service and README documents a Blender export caveat: remove the `glTF_not_exported` node when importing results into Blender. No Unity plug-in or project integration is documented. Unity 6.6 documentation names FBX as its primary model-file format; GLB should be treated as requiring an explicit glTF importer or a tested conversion path. |
| Quality evidence / limitations | Authors’ README provides qualitative comparison imagery and reports 98–133% better skinning accuracy and 17–22% better bone prediction over baselines; these are author-reported claims, not independent tests. It also documents an optional voxel post-process. The repository does not provide a SlopForge-like acceptance guarantee or an automatic deformation-quality gate. |

## Recommendation for SlopForge #14

1. Keep a provider boundary and make TokenRig an opt-in provider running in its own environment/process. It is the more complete, current candidate and the H100 exceeds its published VRAM floor.
2. Preserve the original mesh and texture; request `--use_transfer`; expose `--use_postprocess` as a configurable quality option, not an unconditional fix. Keep original skeleton inputs available for corrective skin-only runs.
3. Validate the returned GLB structurally and produce review poses/evidence; require approval before marking a rig accepted. The upstream repo does not promise deformation quality for generated assets.
4. Add Unity delivery through FBX export or an explicitly selected glTF importer. Do not claim Unity compatibility solely because GLB was produced.
5. Before enabling commercial production by default, resolve training-data provenance/rights and audit dependency licenses. The reviewed MIT declarations cover project code/model-card labels, not necessarily third-party training content.

## ComfyUI-UniRig wrapper audit

The user-provided [PozzettiAndrea/ComfyUI-UniRig](https://github.com/PozzettiAndrea/ComfyUI-UniRig) is a separate ComfyUI wrapper, not the VAST upstream repository. It was checked at commit `69ee59dc459d2da7cb0291930c1f944886c31d7c` (2026-07-31).

- The wrapper is licensed **GPL-3.0** (`LICENSE`, GitHub repository metadata), not MIT. GPL permits commercial use but carries source and notice obligations when conveying covered software. The underlying VAST UniRig code/checkpoint metadata is separately declared MIT.
- The README recommends its **MIA** path for humanoids. The `jasongzy/Make-It-Animatable` model card declares Apache-2.0 and cites `jasongzy/Mixamo` as its dataset. That card does not establish commercial rights to all source animation/character assets. The wrapper's UniRig checkpoints come from `apozz/UniRig-safetensors`, which declares MIT and identifies VAST-AI/UniRig as its base model; the underlying card cites Articulation-XL 2.0. Dataset provenance/rights remain unresolved for both paths.
- This is an inference/rigging extension, not a character mesh generator or hole-repair tool. Its `MIAAutoRig` and `UniRigAutoRig` nodes export rigged FBX files; they cannot make missing torso/limb surfaces appear in an input mesh.
- Its node loader requires the experimental `comfy-env` runtime. `requirements.txt` pins `comfy-env==0.4.1`; `install.py` calls its installer; `prestartup_script.py` calls `setup_env()`. `nodes/comfy-env.toml` declares wildcard `bpy`, `torch-scatter`, `torch-cluster`, `flash-attn`, `cumm`, and `spconv` dependencies and configures an isolated Pixi worker. The root config also declares `ComfyUI-CameraPack`; startup copies bundled sample meshes/animation files into ComfyUI input folders. The manual install instructions run `pip install -r requirements.txt --upgrade` in the ComfyUI environment.
- The inspected H100 runs Python 3.12.3, PyTorch 2.14.0+cu130, and CUDA 13.0. It had no `comfy-env`, UniRig, MIA, or related extension packages installed. A pip dry run of the two Python bootstrap packages showed no proposed PyTorch or NumPy changes, but it cannot establish that the wildcard CUDA wheel set resolves and runs against this H100 stack.

**Decision:** do not install this extension into the working H100 ComfyUI instance yet. This is a compatibility and model-data-rights deferral, not a finding that GPL or Apache prohibits commercial use. Keep Blender Rigify as the current configured provider. Test the wrapper in an isolated ComfyUI clone with pinned worker dependencies and a license-reviewed representative character before making it an opt-in SlopForge provider. Never pass an obviously fragmented candidate into rigging merely to claim an end-to-end pass.

## H100 character smoke

On 2026-10-04 the SlopForge `character_3d_pack` ran through the H100 ComfyUI endpoint with Z-Image Turbo for the concept and TRELLIS.2 BF16 for mesh/PBR generation. The concept was a navy/white lunar scout EVA suit, seed `2941980644`; mesh seed `1149316726`. The generated output had 56,915 faces, one mesh object, five connected texture maps, **1,189 disconnected components**, and **15,402 boundary/non-manifold edges after welding**. Front, side, and rear renders show large missing body surfaces and floating fragments. At the time, structural checks emitted warnings and left the texture candidate reviewable; it was not approved or sent to rigging. A new character topology gate rejects it before material approval. This is a failed quality smoke, not a successful character or rigging result. Test files are in `~/Downloads/SlopForge-H100-character-rig-20261004/` on the developer Mac.

A second H100 inference used Hunyuan3D and produced a visually more complete single-component mesh (57,000 faces after local Blender preparation). This is not a passing character result: the review renders used a neutral gray material, so PBR texture coverage was not assessed. Inspection measured 22 boundary edges and **4,168 non-manifold edges after welding**; the production Rigify provider rejects it, and the new character topology gate blocks it before material approval. A disposable diagnostic copy bypassed only that guard; Blender auto-weighted and exported the FBX and rendered six pose views. The raised-arm and crouch poses moved, but visual inspection found poor elbow/shoulder deformation. This diagnostic is not an acceptable rig and did not change production code. Its report and pose sheet are under `project_hunyuan/rigify-nonmanifold-probe/` in the same Downloads directory. The run's boundary report and preview artifacts are under `results/hunyuan_comparison/`. Inference was served by H100 ComfyUI; Blender preparation and both Rigify attempts ran locally on the Mac.

## Isolated SkinTokens bake-off — 2026-10-04

I cloned the reviewed SkinTokens revision `273b691d35989d71cd17ff2895fdc735097b92d1` to `/tmp` on the H100 and created a separate Python 3.11.17 environment. PyTorch 2.7.0+cu128, `bpy` 5.0.1, and its 1.6 GB inference checkpoints installed without touching ComfyUI's environment. Its requirements omitted `scipy`, and the upstream CLI requests Transformers' `flash_attention_2` backend without declaring/installing FlashAttention. For this evaluation only, I injected a temporary PyTorch SDPA compatibility shim and changed the cloned TokenRig attention setting to `sdpa`; the upstream weights and SlopForge source were unchanged.

SkinTokens completed inference on the same unapproved Hunyuan lunar-scout GLB previously used for Rigify. The output imported into Blender with a 34-bone armature. Its main mesh has 577,042 vertices, 192,966 faces, no unweighted vertices, at most four influences per vertex, and weight sums within 2e-7 of 1. The GLB also includes a hidden, unskinned helper Icosphere in `glTF_not_exported`; this matches the upstream README's Blender cleanup caveat. The model had no approved material texture, so texture transfer was not qualified. Enabling the provider's voxel skin postprocess did not visibly change the pose results.

A same-input disposable Rigify comparison (with only the non-manifold rejection removed from a temporary script) showed severe limb distortion in several review poses. SkinTokens' bilateral elbow and shoulder tests looked materially better after the correct forearm joints were posed. Evidence files and the rendered pose sheets are retained under `~/Downloads/SlopForge-H100-character-rig-20261004/results/{skintokens_evaluation,rigify_same_mesh}/` on the developer Mac.

The cleaned FBX export imported in Unity 6000.6.3f1 as a Generic rig with 34 bones, 34 bind poses, and a skinned renderer. This was a model-import probe only: there was no AnimatorController, animation clip, or in-scene playback. The Unity project and converted FBX are disposable evaluation artifacts under the Downloads results folder.

This is provider inference and comparative deformation evidence, not a passing SlopForge character. The source still fails the animation-readiness/topology gate with 4,168 non-manifold edges; no human approved either output; training-data/commercial provenance is unresolved; and inference required an evaluation-only attention patch. SkinTokens is a promising opt-in bake-off candidate, not a selected/default provider. Finish qualification on a readiness-passing textured generated character using a reproducible runtime, then review representative deformations and validate the rigged export with actual animation playback in Unity.

## Voxel-remesh + Rigify diagnostic — 2026-10-04

To check whether the Hunyuan source's topology was the only barrier, the existing `blender/prepare_model.py --mesh-only` path voxel-remeshed a disposable copy. Blender 5.1 inspection reported one component, 19,582 vertices, 28,500 faces, and zero boundary/non-manifold edges; the SlopForge animation-readiness classifier returned `pass` pending explicit review. Rigify then generated an FBX and all six pose renders. The renders show severe elbow/shoulder deformation and limb stretching, so passing topology and executing a rig provider are insufficient. A deterministic projection bake using the single-view concept tiled the concept visibly over the suit and was rejected as unusable material coverage. The model, pose sheet, reports, and command record are in `~/Downloads/SlopForge-H100-character-rig-20261004/results/voxel_remesh_rigify_probe/`. They remain unapproved evaluation artifacts. The remesh path is diagnostic only and is not enabled as automatic character repair in SlopForge.

SkinTokens then completed inference against the same remeshed GLB using the already isolated Python 3.11 environment and evaluation-only SDPA shim. The reviewed repository revision was `273b691d35989d71cd17ff2895fdc735097b92d1`; checkpoint `experiments/articulation_xl_quantization_256_token_4/grpo_1400.ckpt` had SHA-256 `f4e4706a11cfb520cdde65156a0358545e4fbf8f36237aca01ea5e79d5cb5692`. Input remesh SHA-256 was `b2840d26da101634fc30009f43d92b05673820e5b043662129b3aa894596a6cf`. The main mesh has 85,490 vertices and 28,500 faces; all vertices have weights, with at most four influences and weight sums between `0.9999998625` and `1.0000001192`. The generated 28-bone rig's six gray diagnostic renders show substantially better elbow/arm response than bounds-fitted Rigify on this shape. A cleaned FBX imported into Unity 6000.6.3f1 as Generic with one skinned renderer, 28 bones, and 28 bind poses. Limits remain material: the output contains a helper Icosphere, the rigged mesh has nine components, it has no connected texture, the results have not had human deformation review, and no animation clip/playback was tested. The candidate GLB/FBX, Blender reports, Unity import log, and actual contact sheet are retained in the same `voxel_remesh_rigify_probe/` folder. This makes SkinTokens the strongest provider candidate tested so far, not an integrated/default provider or a passed #14 character.

This run used the same Hunyuan scout after the updated voxel normalization contract, not the earlier coarse mesh. The normalized input SHA-256 is `ad4db23c3f1adf98150c216cec7aff069b9409f432a1f9b68225a7d2a0c696e7`; it has 28,688 Blender faces / 57,376 GLB triangles, one welded component, zero non-manifold edges, and one base-color texture. The first CLI attempt without `PYTHONPATH` failed at the upstream unconditional FlashAttention import before model loading; rerunning with the existing shim completed in about 12 seconds. No ComfyUI or Ollama process was stopped, and no dependency was installed into either service environment.

The packaging script now performs this exact-duplicate weld before component validation. It also recognizes and removes the known unskinned helper Icosphere, rebakes the available base-color channel from the normalized source at 100% reported coverage, and exports a 2.5 MB FBX. The final mesh has 28 bones, no unweighted vertices, at most four influences per vertex, and per-vertex weight sums from `0.9999998509883881` to `1.0000001291773515`. The same-mesh Rigify sheet shows severe limb stretching; the SkinTokens sheet has less visible stretching in the elbow pose. This is not enough to call deformation acceptable: direct Euler rotations on the inferred bone map did not produce a clearly interpretable set of named anatomical poses, and the source color bake is gray with no roughness, metallic, or normal channels. No Unity import/playback was run. See the complete [same-mesh evidence folder](../media/character-qualification-2026-10/same-mesh-budget-skintokens/), including the Blender report and pose/contact images. Decision remains an experimental isolated provider candidate; qualify the pose controls and human deformation before engine validation or approval.
