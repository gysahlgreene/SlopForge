# AI Motion Sources Implementation Plan

> **For agentic workers:** This is a planning document for owner review (2026-10-27). Nothing in it is approved for implementation. When the owner rules on the decisions at the end, turn the chosen packages into tasks with `superpowers:writing-plans` and execute them with `superpowers:subagent-driven-development` or `superpowers:executing-plans`.

**Goal:** Decide how SlopForge gets motion that is not hand-keyed or CMU mocap: text-to-motion for humanoids (NVIDIA Kimodo) and video-to-motion for creatures (a per-creature joint detector reading a two-view AI video), and plan both as pipeline-contract stages with evidence gates, without displacing M3.

**Architecture:** Two tracks that share nothing but the animation library and the Unity delivery. Track A is a new licensed motion source for the existing humanoid retarget (`blender/retarget_mocap.py`). Track B is a new creature pipeline (`slopforge/pipelines/creature.py`, Blender scripts under `blender/`, a remote GPU tool under `processing/`, and video generation on a configured provider). Both run on *providers* the user points SlopForge at (section 3), each with one client, a preflight, a recorded identity and an output-rights status that gates delivery. Every stage records identity, provenance and validation as `docs/PIPELINE_CONTRACT.md` requires; every stochastic stage is a retained candidate with bounded retries.

**Tech Stack:** Python 3.10–3.14, Blender 5.1, SkinTokens (and possibly UniRig) over SSH, [video2rig](https://github.com/canitcode/video2rig) (AGPL-3.0, the transcripts' own tool: a DINOv2-small joint reader trained per creature, two-view fit) as a separately installed tool, PyTorch on a GPU host over SSH, an image-to-video provider (external API or Wan in ComfyUI), Unity 6000.6.3f1 Generic rigs.

**Sources:** the owner's brief `private/research/fable-motion-plan-prompt.txt`; four video transcripts `private/research/ai-video-animation-transcripts.txt` (one developer's reports, unverified); that developer's released tool, video2rig at commit `55d51b3b9685125a8ea27841d6af9523f6352aa1` (2026-10-23, its only commit; README, docs and code read on 2026-10-27); repository contracts, roadmap, docs and code on `origin/main` (`d6a1b55`, 2026-10-26; the local `main` checkout is 98 commits behind, so line references below are `origin/main`). Claims are tagged **[verified]** (with a link), **[reported]** (the developer's claim) or **[hypothesis]** (mine).

## Global Constraints

- M3 is the active milestone (`ROADMAP.md`). Nothing here reorders milestones; section 1 proposes a roadmap change for the owner to decide. Until then only the bounded architectural check in section 10 is allowed, with its question, scope, evidence and stopping point recorded.
- **Product principle (owner, 2026-10-27):** SlopForge is a tool a user points at inference services they are allowed to use, local or remote, and everything it produces must be usable in a commercial game the user sells. The M3 epic's "only MIT or Apache models on the H100" rule was a proxy for that; the real criterion is **outputs shippable in a sold game**, and the proxy is one way to satisfy it (an MIT/Apache model's outputs are cleared by default). Section 3 makes this a gate.
- No inference is submitted, no model is installed and no weights are bundled by this plan.
- Unknown licences, versions and thresholds stay unknown and block the readiness claim they affect (`docs/QUALITY_CONTRACT.md:14-17`).
- Structural, deformation, visual and Unity playback evidence stay separate (`docs/PIPELINE_CONTRACT.md:40-44`). A clip that passes every automatic check is a candidate; a human approves it.
- Credentials never enter the repository, the manifest or provenance records.
- Rejected candidates (rig seeds, clips, detector runs) are retained with their reasons.
- Do not commit anything under `private/`; the transcripts and third-party clips stay there.

7. An artifact whose lineage passes through an `unknown`-rights provider reaching Unity delivery: pin with a lineage fixture where one ancestor is `unknown` and the gate must refuse `approve-texture`, `animation approve` and `unity-setup` while `generate` and review still run (package B0).

## 2. Two tracks, kept separate

### Track A: humanoid text-to-motion (Kimodo)

**What Kimodo is** [verified from the repo and docs, 2026-10-27]: NVIDIA text-to-motion for **humanoids only** (SOMA, Unitree G1 and SMPL-X skeletons; no animal skeleton, so it has no part in Track B), one sentence to a clip of at most 10 s (300 frames at 30 fps), accepting full-body pose keyframes, hand/foot effector targets, 2-D paths and waypoints; outputs NPZ by default and BVH (`--bvh`, SOMA models only, the `somaskel77` skeleton), no FBX; needs about 17 GB VRAM on GPU or under 3 GB with the text encoder on CPU; its text encoder depends on the gated `meta-llama/Meta-Llama-3-8B-Instruct` through LLM2Vec adapters. Licensing is in section 7.

**Where it fits.** Kimodo is a new entry in the animation library, like CMU: a licensed source whose clips are retargeted by the existing Blender retarget and approved by a human. It generates nothing on the SlopForge machine: it runs on an `ssh_gpu` provider (section 3), and SlopForge receives a BVH per candidate.

**Reuse, not duplication.** The developer's five retarget steps map onto what exists:

| Developer's step **[reported]** | Existing | Gap |
| --- | --- | --- |
| Export NPZ (per-bone rotations) | Nothing reads NPZ | Use Kimodo's BVH export (`--bvh`, SOMA models) instead; `retarget_mocap.py` already imports BVH (`:347-348`) with fps from `Frame Time` (30 fps) |
| 22-pair bone map; "leg" naming trap | `CMU_TO_RIGIFY`, `CMU_TO_HUMANOID`, `CMU_TO_GAME_ENGINE` plus source alias tables renamed to CMU names (`retarget_mocap.py:29-68, 366-376`) | Add a `SOMA_TO_CMU` alias table for the `somaskel77` joint names (read from a first export and recorded with the model revision). The alias loop needs the hips bone present and ≥ 4 name matches |
| Bring the target into Kimodo's T-pose, align palms | Limb swing onto the source's joint-to-child directions; torso/neck/head from the actor's average posture over one stride; feet from stance frames (`:435-500`) | None for limbs. Palm alignment: `relax_hands` curls fingers; a palm-orientation step is new only if Kimodo's hand data is used (CMU hands are deliberately unmapped) |
| Copy rotations, move only hips, scale by leg length | Rotation deltas per bone, hips translation only, scale by hip height (`:504-522, 391-395`) | None; hip height versus leg length is a choice, record which |
| Verify every frame that each limb points the same way (worst 3°) | No per-frame pass/fail; metrics only (`:539-545`) | Add `limb_direction_error_degrees` per bone per frame to the report and a limit as an owner threshold (D8) |

The weaker library retarget (`blender/retarget_character_animation.py`, FBX/GLB only, no rest-pose handling) is what `slopforge animation retarget` calls today; the mocap retarget writes only a `.blend` and has no pipeline caller. Track A should give the mocap retarget a pipeline caller and an FBX export rather than teach the library path about rest poses.

**Stage shape.** `motion text <character> "<sentence>" [--count 3]` runs Kimodo remotely with a seed per candidate (if Kimodo exposes one; otherwise the candidate is unseeded and recorded so), downloads each BVH, registers `motion.text.<n>` candidates with the prompt, seed, model id, revision and weights hash, then the existing retarget and review. The gait-cycle detection (`gait_cycle`, `:315-330`) is walk-specific; non-walk clips need `loop` declared or no loop.

**Animation library gap.** The library schema has no licence, source or attribution fields (`slopforge/animation.py:19-65`), and retarget provenance records only provider, source library, clip, path, rig and mapping (`:126-129`). Issue #15 requires provenance to link "source, license, import settings, rig and parent character". Add `licence`, `source`, `attribution`, `generated_by` and `output_rights` (section 3) to the library schema (additive, validated when present) in package B0.

## 3. Provider model

**Principle.** SlopForge does not own inference; the user points it at services they are allowed to use, and it has to produce assets the user can ship in a game they sell. Two things follow: every service is a *provider* with the same minimal contract, whoever runs it; and every output carries a *rights status* that gates delivery, not experimentation.

**Definition.** A provider is anything SlopForge is pointed at by config. Four types cover everything in this plan and everything already in the repository:

| Type | Examples today | Client module (one per type) | Preflight | Recorded identity |
| --- | --- | --- | --- | --- |
| `comfyui` (local or remote) | A ComfyUI on the SlopForge machine or on a remote GPU machine, behind `COMFYUI_URL` (this project's is a remote H100) | `slopforge/backends/comfyui.py` (`ComfyUIClient`) | Health, node classes, model choices, sidecar hashes (`doctor`, `validate_workflow`) | Workflow id + graph sha256, model filenames (weights sha256 from the sidecar or `unavailable`), ComfyUI version/device |
| `hosted_api` | Replicate, fal.ai, BytePlus, Kling, MiniMax (none configured yet) | `slopforge/backends/hosted_api.py` (one client; one adapter class per vendor: `submit`, `poll`, `download`, `identity`) | Credential present (value never read into config), endpoint reachable, model id listed | Vendor, model id string, remote version from the response or `unavailable`, weights hash `unavailable`, request id |
| `ssh_gpu` | SkinTokens host (`tools.skintokens_host`), part masks and OmniPart (`tools.parts_host`); new: detector trainer, Kimodo, UniRig | `slopforge/remote_tool.py` (`run_remote_tool`) plus the provider's install script and self-contained `processing/<tool>.py` | SSH reachable, pinned checkout revision and checkpoint hash match (as `skintokens_runtime.preflight` does) | Tool name, git revision, checkpoint sha256, settings, seed |
| `local_tool` | Blender, rembg/BiRefNet on the SlopForge machine; new: video2rig in its own checkout and venv (below) | `slopforge/backends/blender.py`, `processing/background.py`; new `slopforge/backends/video2rig.py` | Executable found, version read; for video2rig: checkout at the pinned commit, its venv imports, ffmpeg and Blender found, DINOv2 snapshot present | Tool version, script `tool_sha256`, model hash where one is loaded; for video2rig: commit hash, DINOv2-small revision, per-creature reader weights hash |

Every provider record has the same identity shape, `{name, model_id, revision | unavailable, weights_sha256 | unavailable}`, plus the `output_rights` record below. The existing keys (`COMFYUI_URL`, `tools.*_host`) already describe the first two providers; the plan adds a `providers:` map to `ai/project.yaml` that names each one and its type, and package B0 reads the existing keys into it so nothing breaks:

```yaml
providers:
  h100_comfy:   {type: comfyui, url_env: COMFYUI_URL}                      # today's default, named
  rig_host:     {type: ssh_gpu, host: h100-vps-vpn, python: /home/<user>/bin/python, checkout: /home/<user>/SkinTokens}
  motion_host:  {type: ssh_gpu, host: h100-vps-vpn, python: /home/<user>/motion/bin/python, checkout: /home/<user>/motion}
  video_cloud:  {type: hosted_api, vendor: replicate, key_env: REPLICATE_API_TOKEN,
                 models: {walk: wan-video/wan-2.2-i2v-fast}, output_rights: {status: cleared, terms: "Replicate ToS", terms_version: "2026-04-01", read_on: "2026-10-27"}}
```

Stages name the provider they use (`video_generation` uses `providers.video_cloud` or `providers.h100_comfy` with `workflows.video`); compute profiles may swap the provider a stage uses, as they swap workflows today.

**How a user adds their own.** For a `hosted_api` vendor not in the repository: one adapter class with the four methods above, registered by name, plus a `providers.<name>` block with `key_env` and `output_rights`; no stage changes. For an `ssh_gpu` tool: an install script in the house pattern (pinned, import self-check, prints the config lines), a self-contained `processing/<tool>.py` that reads a request and writes `out_dir`, and a `providers.<name>` block. For another ComfyUI: a `providers.<name>` block and workflow sidecars. `doctor` lists every configured provider with its preflight result and its `output_rights` status.

**How the new work fits as providers, not exceptions.** The video client is the `hosted_api` client, used for Replicate, fal or a vendor API; Wan 2.2 in ComfyUI is the same stage on the `comfyui` provider. The detector trainer and reader are one `ssh_gpu` provider (`motion_host`); Kimodo is another `ssh_gpu` provider (`kimodo_host`, or the same host with its own environment); UniRig, if used, is a third. None of them is a special case of `ComfyUIClient`, and `ComfyUIClient` stays the only HTTP client for ComfyUI.

**Proposed `docs/ARCHITECTURE.md` wording (owner decision D13).** Replace the sentence naming `ComfyUIClient` as "the single inference-service boundary for HTTP" with:

> Inference and heavy processing run on *providers* the project configures: ComfyUI services (local or remote) behind `ComfyUIClient`, hosted inference APIs behind `backends/hosted_api.py`, GPU hosts over SSH behind `remote_tool.py`, and local tools. Each provider type has one client module, a preflight that `doctor` runs, and a recorded identity (name, model id, revision or `unavailable`, weights hash or `unavailable`) that every stage using it copies into provenance, together with the provider's output-rights status. Stages depend on the provider contract, not on a vendor. `COMFYUI_URL` and `SLOPFORGE_COMPUTE_PROFILE` keep their roles; a compute profile may choose which provider a stage uses.

**Platform note.** The plan assumes nothing about which machines a user has. Blender steps run on any OS, on the SlopForge machine. CUDA steps (reader training, SkinTokens, UniRig, Wan in ComfyUI) run on whichever NVIDIA machine the user configures, local or remote, as the same provider type (`ssh_gpu` or `comfyui`); a user with one NVIDIA workstation points both at it. video2rig's reading and fitting step is CPU-capable and so runs on the SlopForge machine, but the tool is Windows-tested only: Linux is checked in the spike (step 0), macOS is unknown. SlopForge's install scripts are shell-only today (`scripts/install-*.sh`), so a Windows user runs them under WSL until PowerShell equivalents exist (risk R19, not work in this plan).

### video2rig as a `local_tool` provider

**What it is** [verified from the repository, 2026-10-27]: the developer's own tool from the transcripts, released on 2026-10-23 as one commit (`55d51b3`), AGPL-3.0, 72 stars, no issues, no tags. Python 3.10–3.12, Blender 5.1 ("recent 4.x should work"), PyTorch with CUDA, `transformers>=5`, ffmpeg on PATH, an NVIDIA card of RTX 30 series or newer (it trains and reads in bfloat16). A per-creature joint reader on `facebook/dinov2-small` (Apache-2.0, downloaded from the Hugging Face hub on first use, **not revision-pinned in the code**), a two-panel fit on one CPU thread ("the same motion on every computer"), BootsTAPIR (Apache-2.0, vendored under `third_party/`) as the older, weaker road, UniRig optional for its auto-rig. Everything is a CLI: `blender … export_rig.py`, `blender … render_start.py`, `python -m video2rig.reader.prepare`, `python -m video2rig check|run|review`, `blender … import_motion.py`; a project is one folder per creature (`rig/`, `start/`, `reader/`, `clips/`, `work/`, `out/`). Tested by its author on Windows with Seedance only; Linux paths are handled (`os.name` guards, `~/.cache`, `shutil.which('blender')`, `V2R_BLENDER`), but untested by anyone we know of.

**As a provider.** A `local_tool` provider `providers.video2rig: {type: local_tool, checkout: ~/SlopForgeVideo2rig/video2rig, python: ~/SlopForgeVideo2rig/.venv/bin/python, blender: <existing>, ffmpeg: <path>}`, installed by `scripts/install-video2rig.sh` in the house pattern: clone at the pinned commit, `uv venv` on Python 3.12, `pip install -r requirements.txt` plus the pinned torch wheel, pre-download the DINOv2-small snapshot at a pinned revision and record its sha, run an import self-check, print the config lines. Its preflight checks the commit hash, the venv's imports, ffmpeg, Blender and the DINOv2 snapshot, and refuses a dirty or unpinned checkout. Its identity record is `{name: video2rig, model_id: facebook/dinov2-small, revision: <commit 55d51b3…>, weights_sha256: <reader.pt sha256 per creature>}` with the DINOv2 snapshot revision and sha beside it; a creature's reader is a retained, hashed artifact (`model.detector`), as section 4 already requires. The client `slopforge/backends/video2rig.py` only builds command lines, maps a SlopForge creature's artifacts onto a video2rig project folder under the candidate directory, runs the CLI as a subprocess with the provider's Python, and reads back its JSON (`check.json`, `report.json`, `reader-train.json`) and `.npz` outputs. It never imports `video2rig`, never vendors a file from it, and never patches it in place.

**What the AGPL means here.** video2rig is a separate program that SlopForge invokes and exchanges files with; SlopForge's MIT code is not a derivative of it and stays MIT, as long as nothing imports or links it (Review Focus 6 pins that). For a user running SlopForge on their own machines, AGPL asks nothing beyond keeping the tool's licence and notices. For **anyone offering SlopForge as a service** (a hosted pipeline that runs video2rig for other people over a network), AGPL section 13 applies to video2rig itself: they must offer every user of that service the complete corresponding source of the video2rig they run, including any modification, under AGPL-3.0. That is why the provider runs an unmodified checkout at a pinned commit; a fix we need (a Linux path, a headless option) goes upstream as a pull request or into a published AGPL fork named in the notices, never into SlopForge's tree. The author's plain-words licence section says the same: "Nobody can turn it into a closed paid tool." The AGPL does not reach the outputs (section 7).

### Shippable output as a gate

**The record.** Every provider and every model it serves carries `output_rights`:

```yaml
output_rights:
  status: cleared | attribution_required | restricted | unknown
  terms: "<licence or ToS name>"           # required unless unknown
  terms_version: "<version or date on the text>"
  read_on: "<date the text was read>"
  notice: "<exact notice text>"            # required when attribution_required
  reason: "<why restricted / what is unread>"   # required when restricted or unknown
```

`cleared` means commercial use of the outputs is allowed by terms that were read; `attribution_required` means cleared with a notice that must ship; `restricted` means the terms were read and forbid or condition commercial use (non-commercial, territory, revenue caps); `unknown` means not read or not determinable. (The owner named three statuses; `restricted` is my addition so that a read non-commercial licence is not filed as `unknown`.) The MIT/Apache proxy survives as a default: a model whose weights licence is MIT or Apache-2.0 is `cleared` with `terms` set to that licence, unless its publisher adds conditions.

**Where it lives.** In config, on the `providers.<name>` block and on `models` entries in workflow requirement sidecars (beside the existing `license` field, which keeps meaning "licence to run it"); in `THIRD_PARTY_NOTICES.md` as the human-readable record. In provenance, every stage copies the `output_rights` of each provider and model it used into its `provenance` as `known` facts; an artifact's effective status is the weakest status across its `derived_from` lineage (`output_rights_of(artifact)` walks the lineage: `restricted` < `unknown` < `attribution_required` < `cleared`, and attribution notices accumulate). The animation library's new `output_rights` field carries the same record for imported clips (CMU: `cleared`, terms "CMU statement, free for all uses, not resold").

**What it gates.** Nothing at experiment time: `generate`, `approve` (a mesh candidate), `creature rig`, `creature exam`, `creature video` and `motion text` all run on an `unknown` or `restricted` provider, because the purpose of an experiment is to find out whether a provider is worth clearing. It attaches to the existing approval gates that make an artifact deliverable: `approve-texture` (material candidate → published asset), `animation approve`, `character approve-deformation`, and Unity delivery (`unity-setup`, `approve-texture`'s prefab step). Each refuses with a `configuration` failure naming the artifact, the provider and its status, and the remedy (read the terms and set the status, or regenerate on a cleared provider). `attribution_required` passes, and Unity delivery writes the accumulated notices to `Assets/.../SlopForge-NOTICES.txt` beside the delivered asset so they ship with it. The approval record stores the effective `output_rights` with the other evidence.

**`doctor`.** Reports every configured provider: preflight result, identity, and `output_rights` status with `terms_version` and `read_on`; `unknown` and `restricted` are `WARN` (experiments may proceed), with the line naming what delivery it would block.

**Reconciliation with the quality contract.** `docs/QUALITY_CONTRACT.md:14-17` says unknown requirements block readiness and qualification claims, and `docs/PRODUCT_CONTRACT.md:47-51` lets unknown requirements "permit processing or preview" while preventing a readiness claim. The output-rights gate is that rule applied to a specific requirement: an artifact with `unknown` or `restricted` rights may be processed, previewed and reviewed, but cannot be approved for delivery or counted in a Provisional/Qualified claim, and the protocol record lists output rights among the checked gates. No existing gate is loosened; one requirement that was implicit (the MIT/Apache proxy) becomes explicit and checkable.

## 4. Stage design for Track B

Conventions: every stage is an execution stage (`start_stage`/`begin_stage`/`finish_stage`, `slopforge/manifest.py:211-293`) with `inputs` as artifact refs (`{id, type, stage, path, sha256, attempt, derived_from}`), `settings` as its identity inputs (hashed by `execution_identity`, which drops paths, so content hashes go in), and `provenance` with `known`/`unavailable`/`not_recorded` facts. "Deterministic" means the same inputs and settings give the same outputs on the same tools; "stochastic" means the stage is a candidate generator with a seed where the tool takes one, bounded retries through `slopforge/failures.py`, and retained rejects.

| # | Stage | Required inputs | Retained outputs | Validation boundary (fails closed on) | Identity inputs | Kind |
| --- | --- | --- | --- | --- | --- | --- |
| B0 | Creature mesh | Approved concept, `creature` type | `mesh.final`, maps, readiness report (existing model pipeline) | Existing mesh gates; readiness classifier (`character_readiness.py`) | Existing | As today |

| B2 | Calibrated two-view render | Chosen rig, camera spec | One image: front left, side right, grey background; `cameras.json` (orthographic size, position, axes, image size); video2rig's `rig/` export beside it | Both silhouettes present and inside frame; camera spec validates | Rig hash, camera spec, video2rig commit, Blender/tool hash | Deterministic |
| B3 | Training set | Rig, joint limits (declared per limb or derived from B1 chains), augmentation settings, seed | N renders × 2 views with 2-D joint labels and 3-D truth; `trainset.json` with per-sample seed | Every joint projects inside the image in ≥ 1 view; label count matches bone count | Rig hash, limits, N, augmentation settings, seed, tool hash | Deterministic given seed |

**Rig provider choice.** SkinTokens is the project's provider and is MIT, but its post-processor requires humanoid arms and rejected a non-humanoid skeleton (Rain, `private/research/golden-rig-benchmark-models.md`); whether the model itself rigs quadrupeds is unverified **[hypothesis: the raw GLB may be usable with a generic post-processor]**. ## 5. Evaluation before money

**The exam (B5) as a first-class regression check.** It runs offline from a creature's rig and detector, with no video-model call, and it is the gate before B6 may run for that creature and after any change to the B3–B8 tools:

1. Synthesise a motion: every joint moves at random within its declared limits over K frames, with a seeded generator; optionally a second motion from the procedural gait (M5 package 1) so the exam also covers a real walk.
2. Render it through the B2 cameras (same tool, same settings), with the B3 augmentations applied at the exam's seed.
3. Run B7's consistency metric (should pass by construction) and B8 on the render.
4. Compare per bone against the truth.

Declared metrics, written to `exam.json` and to the manifest stage:

- `joint_position_error`: per joint per frame, 3-D distance between triangulated and true joint, as a fraction of the creature's height; reported as median, 95th percentile and max per joint.
- `bone_rotation_error_degrees`: per bone per frame, the angle between fitted and true bone directions; median, 95th percentile and max per bone.
- `joint_detection_rate`: share of frames in which each joint is detected in both views above the confidence limit.
- `near_far_swap_rate`: for paired limbs, share of frames in which left and right are swapped (the failure the developer saw most **[reported]**).
- `worst_bone`: the bone with the largest 95th-percentile rotation error, named.

Thresholds are owner decisions (D5); the plan invents none. The first spike reports the numbers, and the owner sets limits from them. Every tool change must pass the exam on every creature that has one (`make verify-live` with `SLOPFORGE_RUN_CREATURE_EXAM=1`; the offline `make verify` runs a tiny fixture exam on a synthetic two-bone creature with a stub detector).

**Cross-view consistency (B7), fail-closed.** For each frame and each joint detected in both views, the vertical coordinate must agree: `|y_front − y_side| / height` under a limit (D7), after the calibration from `cameras.json`. Report the share of frames over the limit per joint and overall; a clip over the limit is rejected with `video_views_disagree` and regenerated, never repaired. Also check the two halves are the same creature: silhouette area ratio per frame within a band.

**True frame rate (B7), fail-closed.** Decode the clip, compute mean absolute difference between consecutive frames, and count near-zero differences; if the pattern is periodic (for example two of every five frames are duplicates, 24-in-60), the true fps is the container fps times the distinct share. A true fps that differs from the container fps by more than a tolerance (D7) rejects the clip with `video_frame_rate`, and the recorded fps for B9 is the true one. Also record the container metadata (fps, frame count, codec) as `known` facts.

Both checks run before detection and before any further money is spent on that clip; a provider that keeps producing rejected clips for a motion type is reported, not retried past the bound.

## 11. Risks and open questions

- **R1 Painted-on parts.** TRELLIS.2 paints wings and thin features onto the body; a declared limb without geometry fails B1 by design. Generating real wings is a mesh-route problem (multi-view, part generation) not covered here. Owner question: are winged creatures in M5's scope, or quadrupeds only until the mesh route handles them?
- **R2 Motions no model produced.** The developer found no model that produced a run or a takeoff that agreed across views **[reported]**. The gait fallback (B4) covers walk only; run/attack/takeoff may need hand-keyed or procedural fallbacks or stay out of scope. Owner question: which motions are M5's deliverable?
- **R3 Root motion vs in-place.** The clips are "moving on the spot" by prompt; Unity movement then comes from the controller, and feet slide unless the controller's speed matches the clip's stride (the developer matched speed to leg motion in Unreal **[reported]**). B9 records stride length and period so the Generic controller can set speed; whether to deliver root motion (from the exam's known translation it is derivable only for synthetic clips) is D9.
- **R4 Loop extraction.** Clips are 4–10 s; a walk loop needs plant-to-plant detection like `gait_cycle`, generalised to four feet; non-cyclic motions (attack) need start/end trimming. Short clips may hold under two cycles.
- **R5 Clip length and resolution limits.** Per provider, unconfirmed (MiniMax "2K only" **[reported]**); two views in one frame halve each view's resolution, which bounds detector accuracy on thin legs.
- **R6 Cost per accepted clip.** Unknown until a provider is chosen; the developer paid 9–35 credits per 5 s clip on Higgsfield with retries **[reported]**, and the cheapest model was competitive. Record cost per accepted clip from B5 onward, including rejects.
- **R7 Determinism and pinning.** Closed video models are unseeded and unpinned unless the API says otherwise; option c (Wan in ComfyUI) is the only route with seeds and sha256-pinned weights.
- **R8 SkinTokens on quadrupeds** is unverified; UniRig's skinning degrades on missing tails/wings per its README. The spike answers this first.
- **R9 The detector's generalisation gap.** Trained on renders of the creature, it reads a video model's rendition of the creature; the augmentations are the only bridge. The exam does not measure this gap (it is render-to-render); only real clips do, which is why B6 is gated behind the exam but not proven by it.
- **R10 "IP detected" refusals** and other provider policies on user-supplied images **[reported]**: a refusal is a `candidate_quality` reject with the provider's message, retried once, then reported.
- **R11 Licence drift.** Vendor ToS change; record the ToS version/date read in the notices and re-read before each protocol run.
- **R12 Scope creep into M3.** The spike touches no weapon code; anything beyond it waits for D1.
- **R13 video2rig is one person's one commit.** A single maintainer, one public commit (2026-10-23), no tags, no issues yet, no tests in the repository; its bench is private. Mitigations: pin the commit, keep SlopForge's exam as the acceptance test, keep the own-reader design as the fallback, and treat any upstream change as a new provider revision that re-runs the exam.
- **R14 Seedance-only testing.** The tool's cadence rule ("Seedance clips hold 24 fps content, or 30 with every 5th frame dropped"), its frame-0 alignment ("Seedance re-frames the start image a little"), its prompt advice and its `generate` module are all Seedance-shaped; Kling, Wan and others "work the same way in principle" by the author's own words only. Our intake gates stay independent of it, and the first non-Seedance clips need their own look.
- **R15 video2rig is Windows-first.** Default Blender path, `LOCALAPPDATA` cache and `CREATE_NO_WINDOW` flags are guarded by `os.name`, but only Windows is tested by its author; Linux is checked in step 0 of the spike, macOS is unknown; the UniRig notes describe Windows-only patches.
- **R16 Unpinned backbone at first use.** `facebook/dinov2-small` is loaded without a revision and downloaded on first use; the install script pins and pre-downloads it and the preflight checks the snapshot, else the identity is `unavailable`.
- **R17 AGPL hygiene.** A convenience import, a copied helper or an in-place patch would put SlopForge's MIT licence in question and oblige a service operator to publish more than video2rig; the grep guard and the pinned unmodified checkout are the controls.
- **R18 Its own quality numbers are not gates.** `report.json`'s outline match, twist and jump figures are advisory by the author's design ("a number never replaces watching the result"); SlopForge maps only the ones it can bound to `motion_*` codes and keeps human review.
- **R19 Windows installer gap.** SlopForge's install scripts (`scripts/install-*.sh`, and the planned `install-video2rig.sh`) are shell-only; a Windows user needs WSL until PowerShell equivalents exist. Recorded here as a gap, not as work in this plan.

## Summary for the owner

**The principle, stated.** SlopForge is a tool the user points at inference services they are allowed to use, local or remote, and everything it produces must be shippable in a commercial game the user sells. The M3 "MIT or Apache only" rule was a proxy; the plan makes the real criterion a gate: every provider (ComfyUI, hosted API, GPU host over SSH, local tool) is configured the same way, carries an identity and an `output_rights` status (`cleared`, `attribution_required`, `restricted`, `unknown`), and that status, taken as the weakest across an artifact's lineage, never blocks an experiment but blocks `approve-texture`, `animation approve` and Unity delivery, with `doctor` reporting every provider. Three licence questions are answered separately per component: SlopForge's own code (MIT, unchanged), what the user may run (gated or non-MIT tools are fine as authoring-time tools that never ship), and what rights attach to the outputs that go into the game.

**Roadmap decision (D1):** keep M5's procedural gait as the *first gate* and fallback, and add video-to-motion as M5's second package gated by an offline exam; do not replace the gait, and do not pull Track A (Kimodo, humanoid) ahead of M4. The provider model and its ARCHITECTURE.md wording are a separate decision (D13) that B0 can land now.

**First spike:** adopt the transcripts' own released tool, video2rig (AGPL-3.0, one commit, pinned and never imported), as a `local_tool` provider for the start render, the per-creature DINOv2-small reader, the reading and the fit, and let SlopForge's exam judge it on one generated quadruped (SkinTokens rig, UniRig once if it fails) and the Khronos Fox control, with known motions rendered through its own cameras; step 0 is confirming it installs and trains on the configured GPU provider (Linux, for this project), since its author tested only on Windows; zero video-model cost; every provider used is `cleared`; building our own reader is the fallback if it fails the exam or cannot run headlessly; stops when `exam.json` exists for both or at the first dead end named in section 10.
