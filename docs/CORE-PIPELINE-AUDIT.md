# Core 3D pipeline reliability audit

**Purpose:** implementation audit and ordered work plan for the active core reliability milestone. This is analysis, not a contract or a qualification report. It does not change runtime code or [Current State](../CURRENT_STATE.md). Findings below were established by source inspection; no new assets, live inference, or tests were run for this audit.

The product compass is authoritative. The roadmap calls the active milestone **M0 Core reliability** and the next gate **M1 Props**; “Milestone 1: core reliability” in the request refers to M0 in the checked-in roadmap. This audit uses repository milestone names.

## Current milestone assessment

SlopForge has a functioning synchronous prop path, atomic manifest-file writes, retained concept and mesh candidates, useful structural Blender inspection, ComfyUI preflight, and regression coverage for several known failures. The mask-polarity failure has a controlled recovery report. These are real foundations.

The core reliability contract is not yet satisfied. Most critically, persisted state describes a coarse asset/recipe status and paths; it does not provide a content-addressed history of each execution boundary. The manifest can record hashes for a mesh and its inference input, but not enough links and hashes to establish the full derivation chain or to decide whether every cached output is still valid. Long work is not resumable at its internal stage boundaries. Project acceptance requirements are mostly prompt/taxonomy data and optional structural limits, while `ready` is set without all applicable acceptance evidence.

**Assessment:** functional prototype with useful, bounded reliability protections; not ready to claim core reliability or to begin qualifying props against repeatable pipeline behavior. The likely blocker is state/lineage/invalidation correctness, not a newly established general texture defect. Existing mask recovery proves that failure class for its recorded humanoid cases; the prop route still lacks representative repeatability evidence.

## Audited prop path

The normal CLI path is `generate prop <name> <brief>` → review/select a concept → `approve <name> <candidate>` → review/select a material candidate → `approve-texture <name> <candidate>`. The guided `make` flow wraps these same calls and asks for explicit selections. `generate` creates image candidates; model generation and delivery occur during `approve`, not during the initial image generation. See [CLI dispatch](../slopforge/cli.py#L481), [generation dispatch](../slopforge/cli.py#L782), and [guided review](../slopforge/cli.py#L390).

| Pipeline/category qualified? | Individual model attempt writes `qualified` when it has a structurally viable material candidate. | This is not a pipeline/category status and does not satisfy the quality contract. ## Ordered implementation packages

The order follows dependencies: first make execution state attributable, then use that identity to decide reuse; then make failure/recovery and acceptance decisions on that trustworthy state; only then collect qualification evidence.

### Package 1 — Prop execution lineage and stage journal (**first**)

- **Problem:** current records cannot reliably answer which exact source/config produced each output, and interruption loses in-flight state.
- **Contract:** Pipeline requirements that each stage retains identity, inputs, outputs, provenance, validation and failure state; Product reproducibility/observability.
- **Likely files:** `slopforge/manifest.py`, `slopforge/pipelines/model.py`, `slopforge/candidates.py`, `slopforge/backends/comfyui.py`, `processing/comfy_generate.py`, `processing/comfy_generate_3d.py`, `slopforge/backends/blender.py`, plus tests.
- **Behavior:** for concept → conditioning → mesh/preparation → maps/assembly, persist a stage attempt before expensive work and a terminal result after it, including the internal shape-inference, mesh-preparation, material-inference and output-download boundaries inside `comfy_generate_3d.py`. Store project-relative upstream references with content hashes; effective settings/config identity; source and effective workflow identities; output paths/hashes; known runtime identity or explicit unknown; stage/error/status. Preserve legacy path maps and old history. Do not add qualification semantics in this package.
- **Verification:** mocked deterministic end-to-end prop run; assert one-to-one links from selected concept to mesh attempt to maps/FBX/previews, distinct hashes for changed outputs/config, atomic persistence on success/error, and truthful unknowns. No inference.
- **Dependencies:** none. This creates the input to Package 2.
- **Exit criteria:** after reloading only the manifest and project files, a reviewer can identify every produced prop artifact’s exact upstream content/config and see the last persisted stage state for success and injected failure/interruption.

### Package 2 — Fingerprint-based invalidation and safe prop resume

- **Problem:** recipe status and file existence are used as reuse evidence; `processed_mesh.blend` can outlive its source/config.
- **Contract:** Pipeline requires reuse only for retained valid artifacts and invalidation of affected descendants.
- **Likely files:** `slopforge/pipelines/model.py`, `slopforge/recipes.py`, `slopforge/cli.py`, manifest helpers, Blender stage-cache caller, tests.
- **Behavior:** compare Package 1 input/config/output fingerprints; invalidate descendants in order; resume from earliest incomplete/stale stage; reject corrupt/missing output; explicitly regenerate one stage when requested. Preserve superseded evidence and approved outputs only while their hashes match.
- **Verification:** mutate selected concept, workflow, mesh, and processing settings separately; prove earliest restart and unaffected upstream reuse. Simulate interruption, missing output, altered cached `.blend`, and completed recipe with changed inputs.
- **Dependencies:** Package 1. Package 4 later adds resolved requirement identity to the same invalidation rules.
- **Exit criteria:** no reuse decision is based only on status, candidate count, path, or existence; deterministic tests cover each invalidation boundary.

### Package 3 — Stage failure classification and bounded retries

- **Problem:** errors are broad text; retry boundaries differ between mesh generation, native map processing and swatch processing.
- **Contract:** Pipeline requires earliest failure, actionable remedy, dependent stages not-run/blocked, and no speculative retries on configuration faults.
- **Likely files:** `slopforge/pipelines/model.py`, `slopforge/backends/comfyui.py`, processing wrappers, manifest stage journal, tests.
- **Behavior:** classify a small set of config/environment, inference, candidate-quality, processing/validation, interruption failures. Retry only explicit stochastic candidate failures within configured bounds. Persist each attempt, stage transition, skipped dependency and remedy.
- **Verification:** inject each failure category at each external boundary; assert retries, terminal state, preserved artifacts, and no unnecessary inference.
- **Dependencies:** Packages 1–2.
- **Exit criteria:** every failure has one earliest stage, useful class/message and next action; retries are deterministic and bounded.

### Package 4 — Project requirement resolution and technical readiness gates

- **Problem:** taxonomy prompts and face budgets are not a complete, versioned project/category acceptance profile; automated `ready` can exceed evidence.
- **Contract:** Product project inheritance; Pipeline resolved requirements; Quality acceptance across visual, structural, technical, style, performance and runtime dimensions.
- **Likely files:** project template/config, taxonomy and validation, manifest, `slopforge/pipelines/model.py`, CLI review/approval and tests.
- **Behavior:** represent explicit defaults, project/category requirements, overrides and unknowns. Keep `processed`, `structurally_valid`, `human_approved`, and `ready` evidence distinct (choose compatible persisted forms during implementation); unknown mandatory criteria prevent readiness. Record not-applicable rationale and unchecked gates.
- **Verification:** project fixtures for explicit defaults, overrides, missing limits and unknown requirements; gate tests proving missing/failed requirements cannot yield ready, while structural preview remains usable.
- **Dependencies:** Packages 1–3 provide trusted records and failure states.
- **Exit criteria:** every ready prop has an inspectable set of applicable requirements and satisfied evidence; otherwise status clearly reports why readiness remains pending/unknown.

### Package 5 — Status vocabulary and approval evidence

- **Problem:** candidate structural viability is labeled `qualified`; `ready` and approved markers are not tied to immutable output hashes/reviewer evidence.
- **Contract:** Quality separates asset approval from pipeline qualification; only evidence-backed scoped claims use Experimental/Provisional/Qualified.
- **Likely files:** `slopforge/pipelines/model.py`, manifest compatibility logic, CLI/review board, workflow/agent/setup documentation, tests.
- **Behavior:** rename new candidate state to structural viability; preserve legacy labels on read without promoting them. Bind human material/style decision to exact output hashes, reviewer/authority and the gates reviewed. Do not assign pipeline qualification from asset approval.
- **Verification:** legacy manifest compatibility; tests reject stale approval after in-place file change; CLI/review evidence displays the scope and unchecked gates.
- **Dependencies:** Packages 1 and 4.
- **Exit criteria:** no new candidate uses `qualified`; every approval is auditable and hash-bound; no status implies unchecked gates passed.

### Package 6 — Deterministic core regression and clean-start prop walkthrough

- **Problem:** existing tests cover selected contracts but lack a single deterministic fixture proving their composition across the whole prop path.
- **Contract:** Pipeline verification and recovery; Roadmap M0 exit evidence.
- **Likely files:** focused tests, fixtures, `Makefile` only if needed, operational setup docs.
- **Behavior:** add one representative mock-backed prop run from candidate generation through final material publication; assert state, provenance, validation, approval and recovery. Add interrupted resume / stale-output cases from Packages 1–5. Ensure test uses temporary project paths and no model weights/service.
- **Verification:** `make verify` from documented clean environment; deterministic Blender fixture where available, with skip reasons. A clean-project command walkthrough validates operator docs.
- **Dependencies:** Packages 1–5.
- **Exit criteria:** fast deterministic suite proves success, candidate rejection, external failure, interruption/resume, invalidation, and final approval state without live inference.

### Package 7 — M0 evidence and M1 prop qualification

- **Problem:** no declared-criteria evidence yet demonstrates category repeatability or all claimed downstream gates.
- **Contract:** Roadmap active-core exit and Quality provisional initial protocol.
- **Likely files:** compact public evidence report and previews, only after implementation packages pass.
- **Behavior:** run three representative prop briefs twice independently on one declared workflow/profile/target; record seeds, versions, failures, interventions, review gates and limits. Perform Unity import/runtime checks required by each brief. Six runs are provisional initial evidence, not automatic Qualified status.
- **Verification:** human review of all required gates and evidence completeness; compare outcomes and intervention/failure rates against declared criteria.
- **Dependencies:** Packages 1–6 plus declared prop acceptance criteria.
- **Exit criteria:** M0 reliability claim is bounded by evidence; M1 begins only with declared criteria and a repeatable prop path. If acceptance thresholds remain unknown, record the blocker instead of qualifying.

## First implementation package

Start with **Package 1: Prop execution lineage and stage journal**. It is the prerequisite for knowing whether a texture belongs to a given mesh generation, whether a cached Blender stage still matches its source, whether an interrupted run can restart safely, and which exact graph/environment produced the result. Without that identity, fixing a map failure can still leave stale outputs looking current, and later invalidation tests have no trustworthy oracle.

Keep the first implementation bounded to the existing prop route and existing manifest model. Do not redesign recipe orchestration or introduce a general workflow engine. The first regression should fail if a candidate map is linked to the wrong mesh attempt, if a workflow override changes without changing effective run identity, or if an interruption leaves no persisted stage boundary. Package 2 then consumes this record to add safe reuse.

## Verification strategy

1. **Fast deterministic verification:** `make verify` compiles, runs unit/fixture/CLI tests, checks public Markdown links/private metadata, and checks whitespace. Extend this tier with temporary projects, mocked ComfyUI outputs and injected processing failures to prove state/provenance/retry/invalidation. Use real local Blender only for deterministic geometry fixtures; tests already skip when it is unavailable. It proves implemented invariants, not generative quality.
2. **Integration verification:** run against an installed Blender and a compatible ComfyUI service for workflow graph/node/model-choice preflight and selected deterministic input/output handoffs. `make verify-live` currently opts into actual ComfyUI 2D and 3D inference plus Blender continuation; it does not verify Unity import/Play. Add or run only the integration slice needed by a package, report unavailable coverage, and keep Unity checks separate.
3. **Live generative qualification:** after deterministic contracts pass and prop criteria are declared, run the Quality contract’s three representative briefs with two independent runs each. Record every failure and intervention, versions/config, material/structural review, and required Unity checks. Human appearance review is required; live runs do not replace fixtures, and passing fixtures do not qualify assets.

## Deferred work
